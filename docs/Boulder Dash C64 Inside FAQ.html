Introduction

As a consequence, you should avoid using those names in your software. Several Boulder Dash clones were banned in the past because of inflicting copyrights.

There is no waranty for the information in this document, though it should be fairly accurate. It mainly covers the C64 internals of Boulder Dash. The Atari 400 and Plus/4 versions are almost identical. Other systems usually feature a completely different engine.

The latest version of this document can be found at www.gratissaugen.de/erbsen

All numbers marked with $ as well as memory adresses are given in hexadecimal.

Engine abbreviation:
BD1: Boulder Dash 1
BD2: Boulder Dash 2
PLCK: Peter Liepa Construction Kit
1stB: First Boulder Dash (aka. New Boulder Dash)
CrDr: Crazy Dream
CrLi: Crazy Light

The start signal is another frequently used term in this document. It describes the point in time the cave timer starts. It is accompanied with a crack sound and the status bar changes.
 

The differences between BD1, BD2, PLCK, 1stB, CrDr and the CrLi Engine

  • Amoeba:
    • BD1:
      • The slow growing timer is start immediately (even before the start signal).
    • BD2
      • The timer starts with the first possibility of growing.
    • PLCK
      • Introduces separat time setups for Amoeba and Magicwall.
    • 1stB, CrDr, CrLi:
      • The timer does not start befor the start signal.
  • Destructable titanium wall:
    • BD1, BD2, CrDr
      • Introduced in BD1
      • Was replaced with the hidden exit in PLCK. Has its own element in CrDr, though.
  • Magic wall:
    • BD1:
      • When a Boulder drops into it, the cavescan restarts skipping all the rest of the cave. As a side effect (which was first deployed in BD3) Amoebas beyond that point aren't count, neither is the possibility of growing checked for. Hence, if there is no Amoeba with the ability of growing up to the used Magic Wall, the Amoeba will convert to Diamonds.
      • The timer starts with the first usage (even before the start signal).
    • BD2:
      • The strange timing was removed. As a consequence, it is not possible to convert the amoeba by using a Magic Wall anymore.
    • PLCK:
      • Introduces separat time setups for Amoeba and Magic Wall.
    • 1stB, CrDr, CrLi:
      • The timer does not start before the start signal. It can be still activated before that point, though.
      • There is a new option to convert the Amoeba, no matter where is it.
  • Border behavior:
    • BD1, BD2:
      • The first and last line is included in the code pointer scan, but it is not scanned for the effect table. That means, whenever an element moves to the border, its delay state becomes permanent. In/Out Boxes work correctly on the border.
    • PLCK:
      • The upper and lower border is not scanned at all. Elements can react with items on the border, though. In/Out Boxes don't work on the border. Amoebas are not count there.
    • 1stB, CrDr, CrLi:
      • The border is fully integrated. Items moving out of it are redirected to the opposide border. The interaction is implemented by copying the borders on top/under the opposide border between each scan. This method has side effects, but was choosen due to its fast nature, and in the avarage cave, it is accurate enough.
  • Scrolling:
    • BD1, BD2, PLCK:
      • It starts at the latest Inbox found during setting up the cave.
      • If the cave has more than one Inbox, it scrolls one step for each Rockford making a step. If there are really a lot of Rockfords, this can cause overflows and the game is scrolling back and forth.
    • 1stB, CrDr, CrLi:
      • The game initially scrolls to the first line featuring an Inbox and there to the right most one.
      • As soon as Rockford(s) appear, the game always scrolls to the first found one in each scan.
  • Flashing In/Out boxes:
    • BD1, BD2, PLCK:
      • The state is alternatig on each found activ Box in order. If there is an even number of activ Boxes, they will not flash, but display a pattern of empty and full boxes.
      • Rockford can only appear from its Inbox from its empty state. If there are many Inboxes, this results in a pattern of appearance rather than all Rockfords appearing at once.
    • 1stB, CrDr, CrLi:
      • Flashing is enforced by ensuring the state of the first Box found is alternating between each scan.
  • Growing Wall:
    • BD2, PLCK:
      • It was introduced with BD2, though it was later added to BD1 in some fanmade games. No parameters available. Can only grow horizontal.
      • Except later, the Diego Effects made it possible to let the Growing Wall look like another element, typically a Titanium Wall.
    • 1stB, CrDr, CrLi:
      • The growing direction can be preset and/or switched in game.
  • Slime:
    • BD2, PLCK:
      • It was introduced with BD2, though it was later added to BD1 in some fanmade games. No parameters available except the permeability. It uses the same graphic as the Amoeba.
    • 1stB, CrDr, CrLi:
      • Has its own, independed graphic now. The two elements going through it, can be freely selected.
  • Voodoo Rockfords
    • PLCK:
      • Introduced with PLCK.
      • Later changed to the Mrs. Rockford graphic in many games.
    • 1stB, CrDr, CrLi:
      • Can catch and collect Diamonds now. When destroyed, it converts to a Gravestone surrounded by Titanium Walls and causes a time penalty.
  • Hidden Exit:
    • PLCK, CrDr, CrLi:
      • Introduced in PLCK.
      • Replaces the Destructable Titanium Wall (which has a separate element in CrDr, though)
  • Enemy direction change
    • 1stB, CrDr:
      • If automatic enemy direction change is enabled, the enemy will change direction the first time at the start signal.
    • CrLi:
      • no direction change will occour at the start signal.
  • There are several other elements introduced in 1stB, CrDr or CrLi.

  • General bugs found in several engine

    • Also in two player games, the Inbox is flashing slightly longer, rendering some caves unplayable.

    • The game time is counted in a raster line interrupt, which causes a PAL machine to have only 50 Boulder Dash seconds in a real minute.     • When the screen scrolls left and you're running towards the right, Rockford pauses for one frame when the scroll direction changes.

  • PLCK Construction Kit:
    • Can crash during saving. When this happens, just save the RAM at $be00-$bff0 manually. Alternatively, you can use a cave rescue tool.
    • There are many strange behaviors in the editor.
  • PLCK game modul:
    • Magic Wall has no sound. Bugfix (disk and tape): $401d=$e5; Poke 16413,229
    • The dissolve effect has a really bad bug which causes random adresses overwritten with $7c bytes. Sometimes caves are destroyed that way, somtimes the code is destroyed and the game crashes immediately. Bugfix:
      • disk version: $5663=$ea, $5664=$ea; Poke 22115,234:Poke22116,234
      • tape version: $565d=$ea, $565e=$ea; Poke 22109,234:Poke22110,234
  • 1stB:
    • When the Commodore key is pressed before the start signal, the game does not end as it is supposed to and every diamond counts 500 points.

$20 onwards: cave data, deliminated with $FF.

The cave data (beginning at offset $20) is broken into variable sized records where the first byte contains the object to store (low 6 bits only) and the kind of structure to create (upper 2 bits). Depending on the structure to create, there are 2, 4 or 5 bytes of parameters that follow.
A cave can have up to 255 byte. Valid positions are column=0..39 and row=2..23 whereas 0;2 is the top left corner on the border.

The four structure codes are:

  • 00 = draw a single object
    • param byte 1: column
    • param byte 2: row
  • 01 = draw a line of that object
    • param byte 1: begin column
    • param byte 2: begin row
    • param byte 3: length
    • param byte 4: direction code (0=up, 1=up/right, 2=right, 3=down/right, 4=down, 5=down/left, 6=left, 7=up/left)
  • 10 = draw a rectangle of that object, filled with a second object
    • param byte 1: top left column
    • param byte 2: top left row
    • param byte 3: length
    • param byte 4: height
    • param byte 5: object to fill with
  • 11 = draw a rectangle of that object, don't modify the insides.
    • param byte 1: top left column
    • param byte 2: top left row
    • param byte 3: length
    • param byte 4: height
Decoding "randomly placed" objects
All caves have the opportunity to place up to four objects in "random" positions. They aren't really random, in the sense that the randomiser is set to a given seed value, and probabilities are checked against a given probability code; this way, objects will be "randomly" placed in the same positions each time you try the cave. Method: For each cave position (20 lines x 40 columns), pick a "random" number (0-255). If the random number is less than any of the four probability codes given at offsets $1C to $1F in the cave data, then put the object code given at the corresponding offset from $18 to $1B at the current position. (If the random number is less than more than one of the given probabilities, preference is given to the later object codes - in order of offsets $1B, $1A, $19, $18). Note that after this routine has finished, the bounding steel wall is placed over the extremeties of the cave (effectively DrawRect(0,2,40,22)).

The cave data (beginning at offset $1A) is broken into variable sized records where the first byte is the structure code. Depending on the structure to create, there are 3, 5, 6 or 8 bytes of parameters that follow.
A cave can have up to 250 byte. Valid positions are column=0..39 and row=0..21 whereas 0;0 is the top left corner on the border.
Rockford extended the engine in order to use maps of an object and Construction Kit Caves in the Profiboulder series.
The random number generator works exactly like in BD2 and is also used for the Slime permeability.

The structure codes are:

  • $00 = draw a line of an object
    • param byte 1: object to draw
    • param byte 2: begin row
    • param byte 3: begin column
    • param byte 4: direction code ($00=up, $02=up/right, $04=right, $06=down/right, $08=down, $0a=down/left, $0c=left, $0e=up/left)
    • param byte 5: length
  • $01 = draw a rectangle of an object, don't modify the insides
    • param byte 1: object to draw
    • param byte 2: top left row
    • param byte 3: top left column
    • param byte 4: height
    • param byte 5: length
  • $02 = draw a rectangle of an object, filled with a second object
    • param byte 1: object to draw
    • param byte 2: top left row
    • param byte 3: top left column
    • param byte 4: height
    • param byte 5: length
    • param byte 6: object to fill with
  • $03 = draw a single object
    • param byte 1: object to draw
    • param byte 2: row
    • param byte 3: column
  • $04 = draw a raster pattern of an object
    • param byte 1: object to draw
    • param byte 2: top left row
    • param byte 3: top left column
    • param byte 4: amount of rows
    • param byte 5: amount of columns
    • param byte 6: distance between rows
    • param byte 7: distance between columns
  • $05 = draw a map of an object
    • param byte 1: object to draw
    • param byte 2: amount of values
    • param byte 3: MSB of the target adress ($0850..$0bc0)
    • param byte 4: LSB of the target adress
    • param byte 5 onwards: the map description with LSBs drawn first
  • $06 = add an object relative to another
    • param byte 1: existing object
    • param byte 2: object to draw
    • param byte 3: distance to the right; if the end of the row is reached, the next row is used.
  • $07 = set Slime permeability
    • param byte 1: every bit has an equal value, more bits set to 1 means more delay.

      • The pattern is related to the random number generator and to the seed used for this cave and level.
  • $09 = use a Construction Kit cave
    • param byte 1: LSB of the cave data
    • param byte 2: MSB of the cave data
    • param byte 3: row of the inbox
    • param byte 4: column of the inbox

      • The cave data does not contain the upper and lower borders. The cave description uses the nybble codes defined for the PLCK engine.

CrDr-Engine

Start: $1fa9
Program: $1f00-$cfff (some cave lay inbetween.)
Intro screens may be present at $0c00-$13e8 and will be overwritten during the game.

The cave data (beginning at offset $49) is broken into variable sized records where the first byte is the structure code. Depending on the structure to create, there are 3, 5, 6 or 8 bytes of parameters that follow.
A cave can have up to 1024 byte. Valid positions are column=0..39 and row=0..21 whereas 0;0 is the top left corner on the border.
The random number generator works exactly like in BD2 and is also used for the Slime permeability.

The structure codes are:

  • $01 = draw a single object
    • param byte 1: object to draw
    • param byte 2: column
    • param byte 3: row

    • param byte 1: object to draw
    • param byte 2: top left column
    • param byte 3: top left row
    • param byte 4: length
    • param byte 5: height
  • $03 = draw a filled rectangle of an object
    • param byte 1: object to draw
    • param byte 2: top left row
    • param byte 3: top left column
    • param byte 4: height
    • param byte 5: length
  • $04 = draw a line of an object
    • param byte 1: object to draw
    • param byte 2: begin column
    • param byte 3: begin row

    • param byte 5: direction code relative to $80. (Comon values are $58=up, $59=up/right, $81=right, $A9=down/right, $A8=down, $A7=down/left, $7F=left, $57=up/left)

    • param byte 2: top left column
    • param byte 3: top left row
    • param byte 4: discance between columns
    • param byte 5: distance between rows
    • param byte 6: amount of columns
    • param byte 7: amount of rows
